### Session and restore edge cases

- Internet connect/spawn and late-load bootstrap check Steam validation. LAN mode accepts the claimed ID. Authorization arriving after connect starts the session. The session-created event runs outside its lock. Seed waits for an ordered stats flush, reads the lifetime row using Dapper, checks the session generation and hydrates under the per-player lock. Before a session exists, player mutations have no target. Unseeded sessions accept events but cannot publish lifetime snapshots. See `PlayerLifecycleHandler.cs:56–129` and `PlayerSessionService.cs:60–104,221`.
- A held disconnect normally ends playtime at departure. A reconnect before the seed returns clears the departure timestamp, so the offline interval contributes playtime. In a narrower race, the seed thread removes the old wrapper before publishing its final snapshot. A reconnect on the game thread can enqueue its flush in that gap and read the older database row. Confidence is high in the interleaving and its frequency is unmeasured. Serialize the handoff per Steam ID and test with a gate between removal and enqueue. See `PlayerSessionService.cs:74,148–162` and `PlayerLifecycleHandler.cs:69–76`.
- The README already documents a different problem. An old absolute snapshot from server A can overwrite later play on server B after an outage. The DB fixture wrote 6 and then replayed 3, leaving 3. A player's local version counter is unsuitable as a cross-server ordering key. A durable session identity and deduplicated session deltas would require a migration and parallel comparison before switching readers. See `README.md:159` and `StatsRepository.cs:676`.
- On an accepted restore, the stats worker removes earlier in-batch player-round updates at or beyond the target and deletes persisted rows. The position marker separates pre- and post-restore events and discards voided retries. The backup writes starting lifetime totals, restarts eligible sessions and restores match baselines. Players who joined after that backup and held leavers have incomplete coverage, as acknowledged in `RoundBackupService.cs:143,166`. A completed replay should count the replacement round once. Test a late join, a leaver and a second restore of the same round.
- A human killing an enemy bot receives one kill. With valid baselines and a completed tracked round this adds one lifetime, match and round kill. A bot killing a human gives the human one death. Bots participate in alive counts, opening kills and trades without receiving a player session. With positions enabled, a human killing a bot can create a `players` parent with Steam ID zero for the position FK. All such victims share that ID. See `CombatEventProcessor.cs:251,304,326,367` and `PositionTrackingService.cs:108`.

**Measurement.** Native-free Release .NET 10 capture of ten seeded, dirty players with six weapon keys in each of six histograms. After 1,000 warmups, 5,000 calls to `CaptureSnapshots(true, "match")` allocated 32,592 bytes per call, with median 24.40 µs and p95 34.90 µs. This isolates managed capture with no contention. It excludes engine reads, chat, delta calculation, the database and file sinks. The patch leaves this operation alone. No game-tick latency improvement was measured.

**Stats writer.** The channel holds 1,000 messages by default and accepts 50–5,000 by configuration. Ordinary producers call TryWrite. On refusal the update is dropped and logged. Only flush/control calls asynchronously wait for space. One reader takes batches of up to 100 in its normal loop. It executes lifecycle updates as it encounters them, then bulk writes players, summaries, weapons, analytics and round deltas. Repository calls have separate commit boundaries. Retryable failures retain batches in FIFO order. Reattempts require new work, flush or startup replay. The nominal 50 MiB buffer charges exactly 1 KiB per update, giving approximately 51,200 updates regardless of dictionary sizes. It evicts oldest batches with a critical log. Permanent data errors are isolated by individual update. LOCAL-disabled bulk failures can discard an entire mixed batch. Successful individual poison-row handling lets a flush complete even when some work was dropped. See `PersistenceChannel.cs:82–105,132–198,315–345,407–452`. [Microsoft channel semantics used on .NET 10](https://learn.microsoft.com/en-us/dotnet/core/extensions/channels)

**Position writer.** Its bounded input has at least 100 slots. Producers also use TryWrite. A separate queue retains at most 5,000 retry events. Fresh events have priority, so old retries can starve under sustained input. The reader groups up to 100 by match and event type, isolates rejected rows, and buffers retryable groups with a 5–60 second delay. The marker stops subsequent reads until the delete is processed or deliberately abandoned. Shutdown drains on success and cancels at the deadline. Counts in retry memory and in flight are absent from the shutdown warning. See `PositionPersistenceService.cs:96–180,194–266,275–356`.

**Shared database pipeline.** Three exponential jittered retries start at 200 ms. A shared circuit opens for 60 seconds when at least five attempts in 30 seconds meet a 50% failure ratio. The innermost timeout is five seconds per attempt and depends on cooperative cancellation. Data errors have different handling from repairable schema/grant errors. Explicitly disabling LOCAL causes bulk writes to be dropped. A worker awaiting input or backoff does not consume a game tick. See `src/Infrastructure/ResiliencePolicies.cs:32–120`. [Polly v8 timeout semantics, used with 8.9.0](https://www.pollydocs.org/strategies/timeout.html)

For repair, preserve the unresolved subset plus its match identity without replaying already acknowledged append-only events.

Remote server authentication requires VerifyCA or VerifyFull and appropriate trust material. The documented runtime grants are SELECT, INSERT, UPDATE, DELETE and CREATE TEMPORARY TABLES. ## Cleanup and reachability

- Removed the `weaponStats` local list and its duplicate append at `PersistenceChannel.cs:353,366`. The sole producer appended exactly the same snapshot to both lists in the same switch arm. Both repository consumers enumerate without mutating the source. The worker still awaits summaries, weapons and analytics in that order with the same token and exception path. This removes one list allocation per processing attempt and one append per match-player update.
- Removed the intermediate list of match-start values and the subsequent re-indexing pass at `MatchStatsService.cs:93–101`. Capture and hydration populate the baseline by Steam ID, and the carry/restore paths retain the same ID. The new dictionary copy is taken under the existing lock before clearing the live dictionary. Snapshot capture and queue publication still occur after releasing that lock. Both collections removed by these two cleanups were method locals without external names.
- Removed the redundant recovery save from `SetOverride` after tracing the registered `css_scrim set` command, both config names, all recovery constructors/readers and README's until-reload contract. No JSON field or command was removed. A regression test exercises the real manager with recording recovery.
- Retained all four package references, cfg assets (including externally selectable live_wingman.cfg), embedded schema, seven SQL views, command names, configuration keys, DTO fields and spill discriminators. The CSS loader, DI registrations, Dapper mappings, test reflection, published cfg glob, dashboards and old recovery files consume names outside ordinary C# call graphs. Removing any such public field or view would require deployed configuration/spill samples or a consumer inventory and an explicit compatibility window. No schema, packaging or overload-policy change is part of this patch.

**Deployment scope.** The patch requires a plugin binary replacement between matches. It needs no database downtime, schema migration, config rewrite or spill conversion. Deploying the previous binary between matches rolls back the code. Neither binary can reconstruct historically overwritten weapon breakdowns or lost spill records from current totals alone.

**Remaining verification.** Run a disposable CS2 server on the documented CounterStrikeSharp build with two human clients and a bot.
